# Ostrovok Agent Worker

Самостоятельный Python 3.12 / LangGraph worker. Код, тесты и вспомогательные материалы находятся только в этом каталоге. Backend хранит бизнес-состояние; агент не подключается к БД.

## Быстрый запуск без ключей

Из каталога `agent_worker` в PowerShell:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m pip install --no-deps -e .
.\.venv\Scripts\ostrovok-agent.exe demo
.\.venv\Scripts\python.exe -m pytest -q
```

Linux/macOS: `python3.12 -m venv .venv`, затем используйте `.venv/bin/python` и `.venv/bin/ostrovok-agent`. Runtime-зависимости закреплены в `requirements.txt`, инструменты проверки — в `requirements-dev.txt`.

`demo` по умолчанию строит поездку через две недели относительно текущего времени, печатает JSON с REST-запросом и результирующим снимком. Backend, брокер и ключи ему не нужны. Стабильный пример:

```powershell
.\.venv\Scripts\ostrovok-agent.exe demo --input examples/initial-snapshot.json --now 2026-10-25T12:00:00
```

`--input` принимает строгий JSON полного `init_info`, а не AMQP-задачу. `--now` предназначен только для локального прогона. Скрипт `scripts/export-examples.py` обновляет схемы и примеры из текущих моделей.

Деморежим — ограниченный сценарный адаптер русских формулировок, а не универсальная локальная модель. Поддерживает Москву, Казань, Уфу и Сочи, ISO/полные цифровые даты, число взрослых, бюджет, возраст ребёнка, питомца, сдвиг дат, сохранение отеля по точному названию и просьбу сделать дешевле. Цены и расписания синтетические. Произвольные незнакомые запросы требуют режима `openai` и реального сервиса данных.

## Подключение к команде

Скопируйте `.env.example` в локальный `.env` и заполните настройки только когда будут доступны сервисы. Сам `.env` исключён из Git; шаблон не содержит ключей.

```powershell
.\.venv\Scripts\ostrovok-agent.exe worker
```

| Настройка | Назначение |
| --- | --- |
| `AGENT_MODE=demo/openai` | Явный выбор адаптеров. Автоматического переключения на мок при ошибке API нет |
| `BACKEND_URL`, `AGENT_SERVICE_TOKEN` | REST/SSE backend; токен обязателен для worker в любом режиме |
| `RABBITMQ_URL`, `AGENT_QUEUE` | AMQP URL и существующая очередь `agent.tasks` |
| `PARSER_URL`, `PARSER_SERVICE_TOKEN` | HTTP API данных; обязательный токен в режиме openai |
| `OPENAI_API_KEY` | Обязателен в openai, отсутствует в репозитории |
| `OPENAI_MODEL` | `gpt-6-luna` |
| `OPENAI_REASONING_EFFORT` | `low`; запросы через Responses API, `store=false` |
| `SSE_SILENCE_SECONDS` | 45 секунд без сетевых данных, heartbeat-комментарии считаются активностью |
| `HTTP_TIMEOUT_SECONDS`, `LLM_TIMEOUT_SECONDS` | 20 / 60 секунд |
| `SYNC_TIMEOUT_SECONDS` | 20 секунд на init_info и согласование после записи/конфликта |
| `MAX_LLM_CALLS`, `MAX_SEARCH_CALLS` | 6 / 12 логических вызовов за поколение; SDK имеет один повтор LLM-запроса |
| `MAX_DELIVERY_ATTEMPTS` | 3; использует delivery/acquisition headers quorum queue |
| `RETRY_BACKOFF_SECONDS` | Начальная задержка повторов — 2 секунды |
| `TIMEZONE` | `Europe/Moscow` |

В `demo worker` настоящими остаются backend и RabbitMQ, а понимание текста и данные — синтетические. Не используйте этот режим как незаметную подмену реального поиска.

Docker собирает только агент:

```sh
docker build -t ostrovok-agent ./agent_worker
docker run --rm --env-file ./agent_worker/.env ostrovok-agent worker
```

В контейнере `localhost` относится к самому контейнеру: укажите доступные адреса backend/parser/RabbitMQ. Подключение к общей сети и Compose остаются задачей владельца инфраструктуры.

## Протокол backend v1

Единственный протокол запуска — `agent.tasks` с телом `{"chat_id":1}`. Состояние читается только через `GET /api/v1/chats/{chat_id}/events` с Bearer-токеном. Запись — `POST /api/v1/chats/{chat_id}/messages`, статусы — `POST /internal/v1/chats/{chat_id}/agent`.

- Worker ждёт `init_info`, затем непрерывно читает `new_message`, `changed_travel`, `agent_info`.
- История дедуплицируется по ID. Изменения из операций истории повторно не применяются. Числовые SSE ID последовательны и отличаются от revision.
- Пользовательское событие отменяет текущее поколение. После действия с patch worker ждёт следующий снимок поездки.
- Граф работает с копией снимка. REST-подтверждение не заменяет каноническое состояние: после записи ожидается соответствующий `changed_travel`.
- Сохранение результата, курсора и маркера выполняется атомарно одним `/messages`. `from` клиент не передаёт. `from_revision` обязателен при операциях.
- После неопределённого результата записи worker ищет свой маркер через SSE. Если подтверждения нет, повторная доставка получает новый `init_info`; слепого повтора POST нет.
- При конфликте ревизии прежний результат отбрасывается, граф запускается на новом снимке. `new_messages` при завершении не приводит к ACK.
- Вопрос сохраняется до `waiting_user`. Во время ожидания SSE открыт, доставка не подтверждена, слот worker занят. После перезапуска вопрос не повторяется при том же курсоре.
- Потеря SSE отменяет граф, LLM, Parser и текущую запись. `completed` не отправляется. При успехе ACK выполняется после принятого backend статуса `completed`; при сбое — NACK/requeue, при постоянной ошибке — reject/DLQ.
- 401 прекращает consumer. Удалённый чат прекращает работу и отклоняется без requeue. Ошибка статуса не превращается в успешный ACK.

Массивы patch адресуются по ID, например `/variants/12345`, а не по индексу. Используются `add/remove/replace`, JSON Pointer escaping и проверка итогового документа на копии. Эскиз `sketches/chat_struct.json` с комментариями не загружается как JSON.

Новые обязательные заголовки, lease, `agent.results` и дополнительные backend endpoints не вводятся. Предотвращение двух активных заданий одного чата, атомарность, фильтрация приватных patch в публичной истории и проверка последнего пользовательского ID при `completed` — гарантии backend. Без серверных fencing/idempotency протокол v1 не даёт строгого exactly-once и полной защиты от гонки между проверкой входа и записью.

### Требования к RabbitMQ

Очередь должна быть заранее создана как durable quorum queue с persistent сообщениями, delivery limit и DLQ. Worker проверяет наличие пассивно и не меняет топологию. Использует manual ACK и `prefetch_count=1`.

Настройте broker consumer acknowledgement timeout с запасом больше возможного поиска **и ожидания пользователя**. У ожидания вопроса нет локального дедлайна. Для нескольких одновременных чатов нужны несколько worker; каждый ожидающий вопрос занимает экземпляр. Освобождение delivery при ожидании потребует другого согласованного протокола.

Ограничение повторных доставок после перезапуска опирается на quorum delivery/acquisition headers и политику broker. В версиях RabbitMQ, где NACK не увеличивает delivery-count, необходим acquisition count либо другая серверная ограниченная политика. Один `redelivered=true` не является счётчиком попыток.

## Граф и данные

`context → extract → decide → search → assemble → explain → persist` — настоящий `StateGraph`. `persist` формирует проверенный REST payload; сетевое сохранение выполняет supervisor, который одновременно следит за SSE.

Модель извлекает типизированный `Intent`; исполняемые patch, деньги, ID и расчёты создаёт код. Текущие `basic/additional` имеют приоритет над приватной памятью. Старые текстовые изменения не переопределяют более поздний `user-action`. Память в `additional_hidden.ostrovok_agent` содержит курсор, вопрос, маркер, исключённые направления, ограниченный кеш фактов и ссылки на предложения, без внутреннего chain-of-thought. Другие поля hidden сохраняются. Постоянного LangGraph checkpointer и подключения к БД нет.

`additional/planning_preferences/fields/autonomy` поддерживает `autonomous`, `balanced` (по умолчанию), `guided`. Агент не создаёт UI переключателя. Поля возраста детей, номеров, питомцев, питания, отмены, багажа и сохранённого отеля появляются в публичной группе `travel_details`. Метки и вопросы русские; свободные объяснения OpenAI следуют языку запроса.

Баланс согласовывает выбор направления, если оно неизвестно. Guided дополнительно спрашивает перед поиском с изменившимися параметрами. Autonomous может выбрать направления из предложенных идей, но не угадывает состав гостей, возраст, точные даты или финансовый предел. «Без лимита» должно быть явным решением. Вывод о погоде не делается без источника: согласованный Parser API пока не содержит погоды.

До трёх разных сборок ранжируются по цене, известным условиям питания/отмены и времени дороги. «Дешевле» показывает самый дешёвый доступный вариант; это не обещает цену ниже уже найденного минимума. Для сдвига дат и состава гостей меняются поисковые ключи; снижение бюджета повторно использует ещё действующие факты. Сохранённый отель фильтруется по ID/точному имени и заново проверяется на новых условиях.

Проверки отклоняют неверных гостей, даты, вместимость, отсутствующую обратную дорогу, неправильный маршрут, пересечения времени, истёкшие предложения и известные нарушения жёстких условий. Неизвестная цена не равна нулю, валюты не складываются без курса, цена за ночь не считается стоимостью всего проживания. Неизвестные правила питомцев, сборы и вместимость видны как неподтверждённые условия. `completed=true` означает конец сборки карточки, а не подтверждённую готовность к бронированию.

Трансферы не имеют согласованного endpoint: агент не придумывает стоимость и не подтверждает аэропортовые стыковки без неё. Вариант явно показывает, что трансфер, запас времени и ранний заезд требуют проверки. Корзина, повторная проверка перед покупкой и имитация оплаты — вне этого сервиса.

HTTP-контракт Parser, формы предложений и расширения для сегментов описаны в `PARSER_CONTRACT.md`; он основан на выбранном PDF и изолирован адаптером. Его ещё нужно совместно проверить на реализации Тимура.

## Проверки

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\ruff.exe check src tests
.\.venv\Scripts\ruff.exe format --check src tests
```

По умолчанию все проверки без внешних сервисов: MockTransport для HTTP/Responses, имитация SSE/backend и delivery. Реальный LLM не вызывается. Брокерный тест пропускается без `RABBITMQ_TEST_URL`.

Для отдельного disposable RabbitMQ (официальный образ, случайный localhost-порт, автоматическое удаление контейнера):

```powershell
.\scripts\test-rabbitmq.ps1
```

Можно вместо скрипта задать `RABBITMQ_TEST_URL` **только для тестового vhost** и выполнить `python -m pytest -q -m rabbitmq`. Тест создаёт уникальные очереди, проверяет настоящий ACK, NACK/redelivery и reject/DLQ, удаляет свои очереди. Ключи модели ему не нужны.

Сквозной запуск с сервисами команды и качество ответов реальной GPT-6 Luna остаются интеграционными проверками после появления backend/parser и ключа.
