# Спецификация взаимодействия Backend ↔ Agent Worker — v1

## 1. Назначение

Документ описывает взаимодействие между основным Backend на FastAPI и отдельным микросервисом AI-агента.

**Используемые протоколы:**

- RabbitMQ (AMQP 0-9-1) — распределение заданий между воркерами.
- SSE — единственный канал получения состояния чата и обновлений агентом.
- REST (JSON) — отправка сообщений, изменений состояния и статусов агента.

Backend — единственный источник истины. Агент не обращается к базе данных напрямую.

### Основные правила

1. В RabbitMQ передаётся только `chat_id`.
2. Одновременно над одним чатом должен работать один агент.
3. Агент начинает работу после получения `init_info` через SSE.
4. Агент обязан обрабатывать события, приходящие во время генерации.
5. Все результаты агента сохраняются через REST, а не через SSE.
6. Если SSE-соединение потеряно, агент прекращает текущую работу и возвращает задание в RabbitMQ.
7. Агент отправляет ACK только после успешного завершения обработки чата.
8. `revision` используется при отправке JSON Patch, но не нужен для обычного текстового сообщения.
9. Взаимодействие должно допускать повторную доставку одного `chat_id`.

---

## 2. Список интерфейсов

| Протокол | Метод / очередь | Назначение |
|---|---|---|
| RabbitMQ | `agent.tasks` | Получить `chat_id` |
| SSE | `GET /api/v1/chats/{chat_id}/events` | Получать состояние и изменения |
| REST | `POST /api/v1/chats/{chat_id}/messages` | Отправлять сообщения и JSON Patch |
| REST | `POST /internal/v1/chats/{chat_id}/agent` | Изменять статус агента |

Других endpoint для работы агента не требуется.

В частности, нет отдельных запросов для получения контекста, создания запуска, завершения запуска или чтения истории.

---

## 3. Авторизация

Agent Worker использует сервисный токен:

```http
Authorization: Bearer <AGENT_SERVICE_TOKEN>
```

Backend отличает агента от обычного пользователя по сервисной авторизации.

Для агента разрешено:

- Читать все публичные поля чата.
- Изменять `chat.name` операцией `/chat/name`.
- Читать и изменять `additional_hidden`.
- Изменять `variants`.
- Изменять `basic` и `additional`.
- Отправлять сообщения с `from: "agent"`.
- Изменять поле `agent` через внутренний endpoint.

Обычный пользователь также может изменять `chat.name`, но не получает доступ к `additional_hidden` и не может изменять `variants` или статус агента. Корневой `history` изменяется только отправкой сообщений.

Для SSE агент использует HTTP-клиент с поддержкой streaming и заголовка `Authorization`, а не браузерный `EventSource`.

Сервисный токен передаётся через переменные окружения. В логах он не отображается.

## 4. RabbitMQ

### Очередь

Название: `agent.tasks`

Тип: `quorum`.

Настройки:

- Durable queue.
- Persistent messages.
- Publisher Confirms со стороны Backend.
- Manual ACK со стороны агента.
- `prefetch_count = 1`.
- Настроенный timeout подтверждения задач, превышающий максимальную длительность одной обработки.
- Dead Letter Queue для сообщений, которые нельзя успешно обработать после допустимого числа попыток.

### Формат сообщения

Тело сообщения — JSON:

```json
{
  "chat_id": 1
}
```

Это единственные данные, необходимые агенту для запуска.

Вся актуальная информация о чате будет получена через SSE.

### Получение задачи

После получения сообщения воркер:

1. Извлекает `chat_id`.
2. Подключается к SSE чата.
3. Получает `init_info`.
4. Проверяет текущее состояние агента и необработанные пользовательские сообщения.
5. Начинает или продолжает работу.
6. Сохраняет промежуточные результаты.
7. Завершает работу через `/agent`.
8. После успешного завершения отправляет RabbitMQ ACK.

До шага 8 сообщение остаётся неподтверждённым.

### Повторная доставка

RabbitMQ может повторно доставить задание:

- после падения процесса агента;
- после потери соединения с RabbitMQ;
- после закрытия AMQP-канала;
- после явного `NACK` с `requeue=true`;
- если ACK не дошёл до брокера.

Поэтому обработчик всегда должен быть готов получить чат, который уже частично или полностью обработан.

### Потеря SSE

При потере SSE:

1. Агент немедленно отменяет активную генерацию.
2. Прекращает запуск новых операций и внешних запросов.
3. Не отправляет `completed`.
4. Закрывает или завершает текущие незавершённые операции.
5. Отправляет `NACK(requeue=true)` в RabbitMQ.
6. Освобождает обработчик задачи.

Если AMQP-соединение тоже недоступно, ACK/NACK не отправляется; после закрытия соединения RabbitMQ самостоятельно повторно доставит неподтверждённое сообщение.

**Важно:** нельзя оставлять генерацию работающей после потери SSE. Все фоновые задачи, связанные с чатом, должны быть отменяемыми.

## 5. Постановка задачи со стороны Backend

Когда Backend сохраняет новое сообщение пользователя или действие `user-action`, он проверяет, есть ли уже активное задание для чата.

### Если агент не работает

Backend:

1. Сохраняет сообщение или изменение пользователя.
2. Помечает чат как ожидающий обработки.
3. Публикует `{"chat_id": 1}` в RabbitMQ.
4. После подключения агента предоставляет ему `init_info`.

Backend должен предотвращать создание нескольких одновременно активных заданий для одного чата.

### Если агент работает

Backend:

1. Сохраняет сообщение или изменение пользователя.
2. Не публикует новое задание в RabbitMQ.
3. Отправляет соответствующие события через SSE.
4. Агент получает их и учитывает в текущей работе.

Агент не перезапускается автоматически при каждом новом сообщении. Он самостоятельно корректирует ход генерации.

### Важное условие

Для решения о публикации задания Backend не должен ориентироваться только на текстовое поле `agent.status`.

Нужен внутренний устойчивый признак наличия активного или ожидающего задания для чата. Это внутренняя реализация Backend и не добавляет новых полей в контракт агента.

## 6. SSE

### Endpoint

```http
GET /api/v1/chats/{chat_id}/events
Authorization: Bearer <AGENT_SERVICE_TOKEN>
Accept: text/event-stream
```

Ответ:

```http
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
```

SSE остаётся открытым на протяжении всей обработки чата.

### Особенности для агента

Используется тот же endpoint, что и для Frontend.

Однако Backend учитывает роль подключившегося клиента:

**Frontend получает:**
- `chat`
- `basic`
- `variants`
- `additional`
- `revision`
- `agent`

**Agent Worker дополнительно получает:**
- `additional_hidden`

Агент должен получать полные пользовательские данные и собственную сохранённую память.

### События SSE

| Event | Назначение |
|---|---|
| `init_info` | Полное актуальное состояние чата |
| `new_message` | Новый элемент истории |
| `changed_travel` | Обновлённое состояние поездки и имя чата |
| `agent_info` | Обновление статуса агента |

### 6.1. `init_info`

Первое событие после подключения.

```text
event: init_info
id: 100
data: {"id":1,"revision":19,"chat":{"name":"Поездка в Уфу"},"history":[{"id":1234,"from":"user","message":"Хочу в Уфу"}],"basic":{},"variants":[],"additional":[],"additional_hidden":{"current_task":"Выбор маршрута"},"agent":{"status":"working","status-message":"Анализирую поездку"}}

```

В примере `basic` и другие поля сокращены.

В действительности возвращается **вся актуальная структура чата**, включая корневой `history` и `additional_hidden`.

Агент обязан дождаться `init_info` прежде, чем начинать генерацию.

Именно это событие обеспечивает восстановление после падения предыдущего воркера.

Если в истории и `additional_hidden` уже содержатся результаты предыдущей попытки, агент должен продолжать с учётом этих результатов.

### 6.2. `new_message`

Отправляется при появлении нового элемента истории.

```text
event: new_message
id: 101
data: {"id":1235,"from":"user","message":"Лучше поедем в Казань"}

```

Вариант пользовательского действия:

```text
event: new_message
id: 102
data: {"id":1236,"from":"user-action","operations":[{"op":"replace","path":"/basic/dates/from","value":"29.10.2026"}]}

```

Вариант сообщения агента:

```text
event: new_message
id: 103
data: {"id":1237,"from":"agent","message":"Проверяю гостиницы"}

```

Агент получает события от всех отправителей, в том числе собственные.

**Правила:**

- `from = "user"` — сообщение пользователя.
- `from = "user-action"` — изменение параметров через интерфейс.
- `from = "agent"` — результат агента.
- `message` может отсутствовать.
- `operations` может отсутствовать.
- У агента могут одновременно присутствовать `message` и `operations`.

Агент добавляет новый элемент истории в локальное состояние, если такого ID ещё нет.

Изменения состояния из `operations` повторно применять не нужно: для состояния используется `changed_travel`.

### 6.3. `changed_travel`

Событие отправляется после изменения структуры поездки.

```text
event: changed_travel
id: 104
data: {"revision":20,"chat":{"name":"Поездка в Уфу"},"basic":{},"variants":[],"additional":[],"additional_hidden":{}}

```

Backend отправляет полные:

- `chat` (включая актуальное имя)
- `basic`
- `variants`
- `additional`
- `additional_hidden` — только агенту
- `revision`

Агент заменяет соответствующие локальные поля, если новая `revision` больше текущей.

Агент не должен самостоятельно применять JSON Patch из `new_message`, поскольку это приведёт к риску двойного применения изменений.

### 6.4. `agent_info`

```text
event: agent_info
id: 105
data: {"status":"working","status-message":"Сравниваю гостиницы..."}

```

Возможные значения `status`:

- `idle`
- `working`
- `waiting_user`
- `completed`
- `error`

Это информационное событие. Само по себе его получение не является подтверждением задания в RabbitMQ.

### 6.5. Порядок событий

Backend гарантирует для каждого чата последовательную нумерацию SSE-событий.

Если сообщение изменило состояние, Backend отправляет:

1. `new_message`
2. `changed_travel`

Если изменился только статус:

1. `agent_info`

`init_info` должен представлять согласованный снимок данных. После него клиент должен получить все изменения, произошедшие позднее снимка.

Агент обрабатывает события в порядке получения.

### 6.6. Обрыв соединения

SSE считается потерянным при:

- закрытии HTTP-соединения;
- ошибке чтения stream;
- завершении stream со стороны сервера;
- превышении тайм-аута отсутствия событий или heartbeat;
- нарушении формата потока, из-за которого дальнейшая синхронизация невозможна.

Backend отправляет SSE heartbeat-комментарии, например:

```text
: ping

```

Рекомендуемый интервал heartbeat — 15 секунд, а тайм-аут отсутствия данных на стороне агента — 45 секунд. Эти значения конфигурируемые.

При потере SSE агент не пытается продолжать генерацию со старым состоянием. Текущая доставка RabbitMQ прекращается и повторно ставится в очередь.

## 7. POST `/api/v1/chats/{chat_id}/messages`

Основной endpoint для сохранения результатов агента.

Используется тот же маршрут, что и у Frontend. Разрешения определяются по авторизации.

### Общий формат запроса

```json
{
  "message": "Текст сообщения",
  "from_revision": 19,
  "operations": []
}
```

Поля:

| Поле | Тип | Обязательность |
|---|---|---|
| `message` | string | Необязательно |
| `operations` | array | Необязательно |
| `from_revision` | integer | Обязательно, если есть `operations` |

Хотя бы одно из `message` или непустого `operations` должно присутствовать.

`from` не передаётся: Backend определяет его по сервисному токену и устанавливает `agent`.

### 7.1. Только сообщение

```json
{
  "message": "Нашёл несколько гостиниц в Казани."
}
```

Ответ `201`:

```json
{
  "id": 1238,
  "revision": 20
}
```

`revision` не изменяется, поскольку состояние поездки не изменялось.

### 7.2. Только изменения

```json
{
  "from_revision": 20,
  "operations": [
    {
      "op": "replace",
      "path": "/basic/cost_range",
      "value": "35000–42000 ₽"
    }
  ]
}
```

Ответ `201`:

```json
{
  "id": 1239,
  "revision": 21
}
```

Backend сохраняет операции в корневой `history` как элемент с `from: "agent"`.

Агент может изменить имя чата операцией `{"op":"replace","path":"/chat/name","value":"Выходные в Уфе"}` с актуальным `from_revision`. Изменение попадёт в `changed_travel` и список чатов.

### 7.3. Сообщение с изменениями

```json
{
  "message": "Добавил вариант поездки в Уфу.",
  "from_revision": 21,
  "operations": [
    {
      "op": "add",
      "path": "/variants/-",
      "value": {
        "id": 12345,
        "name": "Выходные в Уфе",
        "location": "Россия, Уфа",
        "price": "35000 ₽",
        "dates": {
          "from": "1 ноября",
          "to": "2 ноября"
        },
        "completed": false,
        "description": "Поездка на выходные",
        "urls": [],
        "habitations": [],
        "transports": [],
        "additional": []
      }
    }
  ]
}
```

Ответ `201`:

```json
{
  "id": 1240,
  "revision": 22
}
```

### 7.4. Работа с `additional_hidden`

Агент может сохранять там промежуточные результаты.

```json
{
  "from_revision": 22,
  "operations": [
    {
      "op": "add",
      "path": "/additional_hidden/current_task",
      "value": "Поиск гостиниц в Уфе"
    },
    {
      "op": "add",
      "path": "/additional_hidden/completed_steps",
      "value": [
        "Выбраны даты",
        "Найден транспорт"
      ]
    }
  ]
}
```

`additional_hidden` хранится на Backend и доступен через SSE только агентам.

Сохранённые там сведения не должны считаться источником истины для пользовательских параметров, которые находятся в `basic`, `variants` и `additional`.

### 7.5. JSON Patch и идентификаторы

Используется JSON Patch (RFC 6902) с **проектным расширением адресации массивов по `id`**.

Например:

```json
{
  "op": "replace",
  "path": "/variants/12345/completed",
  "value": true
}
```

Здесь `12345` — поле `id` нужного объекта, а не индекс массива.

Другой пример:

```json
{
  "op": "replace",
  "path": "/additional/group_city_restrictions/fields/f1/value",
  "value": 123
}
```

Backend разрешает такие пути, находя элементы массивов по `id`.

Добавление в конец массива:

```json
{
  "op": "add",
  "path": "/variants/-",
  "value": {
    "id": 12346,
    "name": "Другой вариант поездки"
  }
}
```

Для полных объектов сохраняются требования основной схемы данных чата. Сокращённый объект в последнем примере допустим только если Backend разрешает частично заполненные варианты и заполняет остальные обязательные поля значениями по умолчанию.

Поддерживаются операции `add`, `remove`, `replace`. Для MVP операции `move`, `copy`, `test` не обязательны.

Все операции одного запроса применяются атомарно и последовательно.

### 7.6. Работа с `from_revision`

Агент берёт текущую `revision` из SSE.

При отправке операций передаёт её как `from_revision`.

Если ревизия совпадает:

- Backend применяет операции.
- Сохраняет новый элемент истории.
- Увеличивает `revision` на 1.
- Возвращает успешный ответ.
- Рассылает SSE-события.

Если не совпадает, Backend возвращает `409`:

```json
{
  "error": {
    "code": "version_conflict",
    "message": "Chat state has changed",
    "details": {
      "expected_revision": 21,
      "current_revision": 23
    }
  }
}
```

Агент должен:

1. Не считать операции сохранёнными.
2. Дождаться актуального состояния через `changed_travel`.
3. Проверить, сохраняется ли смысл планируемого изменения.
4. При необходимости пересоздать патч.
5. Повторить запрос с новой `from_revision`.

Если SSE недоступен, агент прекращает работу согласно разделу 6.6.

Нельзя автоматически заменять старую ревизию новой, не проверив операции.

### 7.7. Согласованность данных

Backend обязан сохранить сообщение и все его операции одной атомарной транзакцией.

Frontend и Agent Worker не должны наблюдать частично применённое изменение.

После успешного ответа REST обновлённое состояние будет передано SSE-подписчикам.

Агент может обновить локальное значение ревизии из REST-ответа, но для остальных полей авторитетным остаётся полученный через SSE снимок.

## 8. POST `/internal/v1/chats/{chat_id}/agent`

Endpoint для изменения состояния работы агента.

В отличие от `/messages`, этот endpoint не создаёт автоматически сообщение в истории чата.

### 8.1. Работа

```json
{
  "status": "working",
  "status-message": "Подбираю гостиницы..."
}
```

Ответ `200`:

```json
{
  "status": "working",
  "status-message": "Подбираю гостиницы..."
}
```

Backend обновляет `agent` и отправляет SSE-событие `agent_info`.

Статус можно обновлять многократно во время генерации.

### 8.2. Ожидание пользователя

```json
{
  "status": "waiting_user",
  "status-message": "Уточните максимальный бюджет"
}
```

Ответ `200`:

```json
{
  "status": "waiting_user",
  "status-message": "Уточните максимальный бюджет"
}
```

В текущей версии `waiting_user` является промежуточным статусом, а не завершением RabbitMQ-задания.

Агент остаётся подключённым к SSE и ожидает нового пользовательского сообщения. После его получения возвращается к `working`.

Для освобождения воркера во время долгого ожидания потребуется отдельное правило завершения задания; в MVP это не реализуется.

### 8.3. Завершение работы

Чтобы избежать потери нового сообщения пользователя, агент должен указать последний **обработанный пользовательский элемент истории**.

```json
{
  "status": "completed",
  "last_processed_message_id": 1241
}
```

Под пользовательскими элементами понимаются записи с:

- `from: "user"`
- `from: "user-action"`

Сообщения самого агента не учитываются.

### Проверка завершения на Backend

Backend атомарно проверяет:

1. Все пользовательские сообщения и действия до текущего момента обработаны.
2. `last_processed_message_id` совпадает с последним пользовательским элементом истории.
3. Для чата нет более нового пользовательского ввода, требующего обработки.

Если всё верно, Backend устанавливает `completed` и возвращает:

```json
{
  "status": "completed"
}
```

После этого агент отправляет RabbitMQ ACK.

Если пользователь успел отправить новое сообщение:

HTTP `409 Conflict`:

```json
{
  "error": {
    "code": "new_messages",
    "message": "New user messages require processing",
    "details": {
      "last_processed_message_id": 1241,
      "latest_message_id": 1243
    }
  }
}
```

Агент **не отправляет ACK**.

Он продолжает обработку, получает новые события через SSE и позже повторяет запрос `completed`.

Если пользовательских сообщений ещё нет, `last_processed_message_id` допускает `null`.

### 8.4. Ошибки

```json
{
  "status": "error",
  "status-message": "Не удалось обработать запрос"
}
```

Ответ `200`:

```json
{
  "status": "error",
  "status-message": "Не удалось обработать запрос"
}
```

Статус `error` сообщает Backend и Frontend об ошибке, но **не подтверждает успешную обработку RabbitMQ-задания**.

При временной ошибке воркер должен прекратить текущую попытку и организовать повторную доставку.

При постоянной ошибке нужна ограниченная политика повторных попыток и Dead Letter Queue, иначе задание может бесконечно повторяться.

---

## 9. Работа при изменениях во время генерации

Агент должен одновременно выполнять две независимые задачи:

1. Читать SSE и обновлять локальное состояние.
2. Выполнять AI-генерацию и внешние запросы.

Обе задачи работают внутри одной области отмены.

### Новое сообщение пользователя

Если приходит:

```text
event: new_message
data: {"id":1242,"from":"user","message":"Нет, лучше в Казань"}

```

Агент обязан учитывать это при последующей работе.

Он может:

- Отменить текущий LLM-запрос.
- Дождаться окончания текущего шага.
- Изменить дальнейший план.
- Уточнить детали у пользователя.

Конкретная стратегия зависит от реализации агента.

Однако он не имеет права считать текущую работу завершённой, не обработав поступившее пользовательское событие.

### Изменение пользовательских параметров

Если пришёл `changed_travel` после `user-action`, агент обновляет состояние и пересматривает дальнейшие действия.

Например, если пользователь исключил Европу из `locations_tree`, агент не должен продолжать предлагать европейские направления на основании устаревших данных.

### Собственные изменения агента

Агент получает через SSE и собственные сообщения.

Они должны учитываться при синхронизации истории, но не рассматриваться как новый пользовательский запрос.

---

## 10. Восстановление после падения

Новый воркер может получить тот же `chat_id`.

После подключения к SSE он получает полный `init_info` и должен восстановить контекст из:

- `history`
- `basic`
- `variants`
- `additional`
- `additional_hidden`
- `agent`

Если часть работы предыдущего воркера уже сохранена, новый агент не должен без необходимости выполнять её повторно.

Для этого рекомендуется регулярно сохранять существенные промежуточные результаты в `additional_hidden`.

Например:

```json
{
  "current_task": "Подбор гостиниц",
  "completed_steps": [
    "Выбраны даты",
    "Найден транспорт"
  ],
  "next_step": "Проверить стоимость проживания"
}
```

Это не требует сохранения внутренних рассуждений LLM. Достаточно хранить полезные результаты, текущую цель и оставшиеся действия.

### Повторная доставка после completed

Возможна ситуация:

1. Агент отправил `completed`.
2. Backend сохранил его.
3. Агент упал до RabbitMQ ACK.
4. RabbitMQ повторно доставил `chat_id`.

Новый агент получает `init_info`.

Если статус `completed` и новых необработанных пользовательских сообщений нет, он сразу отправляет ACK без запуска генерации.

Если новые пользовательские сообщения уже существуют, он начинает их обработку.

---

## 11. Ошибки HTTP

Все ошибки имеют единый формат:

```json
{
  "error": {
    "code": "error_code",
    "message": "Описание ошибки",
    "details": {}
  }
}
```

| HTTP | Значение | Действие агента |
|---|---|---|
| `200` | Успешно | Продолжить |
| `201` | Сообщение сохранено | Продолжить |
| `400` | Ошибка формата запроса | Исправить запрос |
| `401` | Неверный сервисный токен | Остановить воркер, сообщить об ошибке конфигурации |
| `403` | Нет прав | Остановить текущую попытку |
| `404` | Чат удалён | Прекратить генерацию |
| `409` | Конфликт ревизии или новые сообщения | Синхронизироваться через SSE и повторить |
| `422` | Неверные данные или JSON Patch | Исправить запрос |
| `500` | Внутренняя ошибка | Ограниченные повторы |
| `503` | Backend недоступен | Прекратить попытку и повторить позднее |

HTTP-ошибка не означает автоматически, что запрос не выполнился. Например, соединение могло оборваться уже после успешного сохранения сообщения.

Поэтому после неопределённого результата агент должен сначала сверить актуальное состояние через SSE, а не безусловно повторять тот же изменяющий запрос.

---

## 12. Состояния агента

Основная последовательность:

```text
idle → working → completed
```

Дополнительные состояния:

```text
working → waiting_user → working
working → error
```

`working` означает активную работу или обработку задания.

`waiting_user` означает, что агент временно ожидает новый пользовательский ввод, сохраняя задачу и SSE-подключение.

`completed` означает, что текущий пользовательский ввод полностью обработан.

`error` означает неуспешную обработку.

При потере SSE агент не устанавливает `completed`, даже если генерация почти закончена.

---

## 13. Ответственность Backend

Backend должен обеспечить следующие гарантии:

1. Все пользовательские изменения сохраняются до публикации событий.
2. Для чата не создаются несколько независимых активных заданий.
3. `init_info` содержит согласованное состояние.
4. Агент получает `additional_hidden` через SSE.
5. SSE передаёт события в правильном порядке.
6. Все JSON Patch применяются атомарно.
7. Адресация элементов массивов по ID работает одинаково для пользователя и агента.
8. Backend проверяет `from_revision`.
9. Endpoint `/agent` атомарно проверяет последний обработанный пользовательский элемент истории при `completed`.
10. При потере воркера или неудачной доставке задача может быть повторно обработана.
11. Обычным пользователям не раскрывается `additional_hidden`.
12. Новый пользовательский ввод после `completed` инициирует новую обработку.

Надёжная публикация задания в RabbitMQ после сохранения сообщения — ответственность Backend. Для этого можно использовать сохранённый флаг ожидающего задания и повторную публикацию при необходимости.

---

## 14. Ответственность Agent Worker

Разработчик агента реализует:

1. Подключение к RabbitMQ.
2. Получение и подтверждение заданий.
3. SSE-клиент с Bearer-авторизацией.
4. Разбор `init_info`, `new_message`, `changed_travel`, `agent_info`.
5. Локальное актуальное состояние чата.
6. Асинхронную генерацию с возможностью отмены.
7. Отправку сообщений и JSON Patch.
8. Обработку конфликтов `from_revision`.
9. Отправку статусов через `/agent`.
10. Проверку новых пользовательских событий перед завершением.
11. Немедленную отмену работы при потере SSE.
12. Повторную доставку задачи при неуспешной попытке.
13. Восстановление работы из сохранённого состояния.
14. ACK только после успешного `completed` или подтверждения, что ранее завершённое задание больше не требует работы.

## 15. Итоговая последовательность

```text
Frontend                Backend              RabbitMQ           Agent
   |                       |                     |                |
   | POST /messages        |                     |                |
   |---------------------->|                     |                |
   |                       |                     |                |
   |                       | publish chat_id     |                |
   |                       |-------------------->|                |
   |                       |                     | deliver        |
   |                       |                     |--------------->|
   |                       |                     |                |
   |                       | GET /events (SSE)                    |
   |                       |<------------------------------------|
   |                       |                                     |
   |                       | init_info                           |
   |                       |------------------------------------>|
   |                       |                                     |
   |                       | POST /messages                      |
   |                       |<------------------------------------|
   |                       |                                     |
   | changed_travel        | changed_travel                      |
   |<----------------------|------------------------------------>|
   |                       |                                     |
   | POST /messages        |                                     |
   |---------------------->|                                     |
   |                       | new_message                         |
   |                       |------------------------------------>|
   |                       |                                     |
   |                       | POST /agent completed               |
   |                       |<------------------------------------|
   |                       |                                     |
   |                       | 200 OK                              |
   |                       |------------------------------------>|
   |                       |                     | ACK            |
   |                       |                     |<---------------|
```

Если SSE теряется, вместо завершения:

```text
SSE disconnected
    ↓
Cancel generation
    ↓
NACK(requeue=true)
    ↓
RabbitMQ redelivers chat_id
    ↓
Another worker receives init_info
    ↓
Continue from saved state
```

**Итого:** RabbitMQ нужен только для доставки `chat_id`; SSE — для непрерывного чтения всего актуального состояния; `/messages` — для записи результатов; `/agent` — для управления статусом и завершением обработки.
